# Задача: P-AUDIT — повторный аудит 21 расхождения против текущего HEAD

> **Статус задачи:** ready · **Зависимости:** нет (вход для P1/P2/P3)
> **Создан:** 2026-07-15

## Роль
Ты — независимый технический аудитор проекта Steersman Desktop
(Tauri 2 + React 19 + Rust, порт Hermes Agent). Производишь read-only
сверку контракта. НЕ пишешь код, НЕ делаешь фиксов — только верификация
и отчёт.

## Контекст (читай перед работой — обязательно)
1. `docs/plans/ADR-004-ws-transport-contract.md` — **АКТУАЛЬНЫЙ**
   транспортный контракт (hermes serve + WS /api/ws). Ground truth.
2. `docs/plans/ADR-002-*.md` и `ADR-003-*.md` — **частично устарели**
   (см. warning-блок в SDD §7). Транспортные части (HTTP 8642, API_SERVER_*,
   /v1/runs) НЕ существуют в живой установке.
3. `SDD.md` §7 — таблица 21 расхождения; пункты с маркером 🚫 невалидны для
   WS-транспорта.
4. Phase 0 уже выполнена: `chat.rs` имеет `parse_ws_message` + переключатель
   `STEERSMAN_TRANSPORT`, есть модуль `ws_transport.rs`. Тесты зелёные.
5. Тех-стек: Tauri 2, Rust 2021, React 19, Zustand 5, tokio, reqwest, tokio-tungstenite.

## Проблема
SDD §7 содержит 21 пункт из аудита 2026-07-12. С тех пор:
- ADR-004 supersede'нул транспортную часть ADR-002/003;
- коммит `6ce9fb4` уже закрыл часть пунктов (reasoning_effort формат, transport A);
- Phase 0 добавила WS-парсер и WS-клиент.
Команда не знает, какие из 21 пункта ещё актуальны, а какие уже закрыты
или стали нерелевантны. Работа по устаревшим пунктам = потерянное время
(как это случилось с исходным P0).

## Задача
Для КАЖДОГО из 21 пункта SDD §7.1–§7.4 (плюс §7.5 dead code, §7.6 config_health)
выдать вердикт в таблице:

| # | Пункт SDD | Вердикт | Доказательство (команда + вывод) | Действие |
|---|-----------|---------|----------------------------------|----------|

Вердикты строго из списка:
- **CLOSED** — уже сделано в коде. Привести file:line и короткую выдержку.
- **INVALID** — основан на устаревшем ADR-002/003; endpoint/контракта нет
  в живом Hermes (8642, /v1/runs, API_SERVER_*). Привести доказательство
  отсутствия (curl HTTP 000 / grep 0 совпадений).
- **SUPERSEDED** — закрыт иначе, чем предполагал аудит (напр. transport A
  теперь не нужен, т.к. WS даёт tool events напрямую).
- **VALID** — реальный дефект на текущем HEAD. Это кандидаты в P1/P2/P3.
- **PARTIAL** — часть сделана, часть осталась. Указать что именно осталось.

## Метод верификации (обязательный)
- НЕ доверяй SDD/ADR-002 слепо. Для каждого пункта — grep/curl/чтение кода
  на текущем HEAD.
- Для транспортных пунктов — сверяйся с ADR-004, не с ADR-002.
- Для каждого VALID/PARTIAL — точный file:line и одна фраза, что именно не так.
- Запусти `cargo test --lib` и зафиксируй количество тестов (база для регрессии).

## Definition of Done
1. Таблица вердиктов по всем 21 + §7.5 + §7.6 пунктам.
2. Отдельный список VALID+PARTIAL дефектов — это вход для P1/P2/P3.
3. Обновлённый SDD §7: статус каждого пункта дописан в колонку
   (CLOSED/INVALID/SUPERSEDED + дата проверки 2026-07-15).
4. ADR-004 дополнен списком того, что Phase 0 уже покрыла.
5. Никаких правок кода — только docs + отчёт.

## Ограничения
- Read-only по коду. Правки только в SDD.md / ADR-004 (статусная разметка).
- Если пункт нельзя проверить без живого Hermes — помечай NEEDS-RUNTIME,
  не угадывай.
- Не пересобирай ADR-002/003 — они зафиксированы как исторические.

## Что отличает от наивного аудита
Исходный P0 провалился из-за доверия устаревшему аудиту. Этот промпт
требует: *сначала свериться с ADR-004 + кодом на HEAD, потом выносить вердикт*.
Любой пункт «CLOSED» должен сопровождаться file:line + цитатой кода.
Любой «INVALID» — curl/grep доказательством отсутствия endpoint'а.
